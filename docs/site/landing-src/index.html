01 · Persistent workspaces

The sandbox goes. The files stay.

Compute is disposable. Files are not. A workspace is durable storage that lives apart from compute: a directory you already have, or one Sandcrab manages for you. Sandboxes mount it, change it, and disappear. Nothing runs while it waits, so idle cost is zero.

  • The host can reach in between turns. Put, read or delete files while no sandbox is running: drop in an attachment, collect an output.
  • Read-only window, read-write door. Each mount is ReadOnly or ReadWrite, enforced by the kernel. One writer at a time.
  • Swap the shell, keep the burrow. Turn one in python-dev, turn two in render, same workspace.
  • Built for hostile files. Host-side file operations are fd-relative and refuse symlink escapes, because a workspace is attacker-controlled.

Burrow. Crabs come and go. The crates stay.

02 · Backends

Pick your shell: fast container or sealed microVM

Backends plug in behind one trait and report what they actually isolate. You choose explicitly. Sandcrab never moves you from a jar to a tide pool behind your back.

Production

Docker

Shared kernel · single-tenant and trusted hosts

Officially supported and hardened: all capabilities dropped, no-new-privileges, pinned images, loopback-only ports. Spawn→ready about 230–260 ms, teardown about 100 ms. It shares the host kernel, so it is not hardware isolation: use it for your own agents and trusted workloads, not strangers’ code.

  • Explicit selection only: you name the backend, every time
  • All capabilities dropped, no-new-privileges, no privileged mode
  • Network off by default; PID, memory and CPU limits; no swap
  • Runs as your uid, so workspace files stay editable on the host
  • Template image must match its pinned SHA-256
Built · KVM tests pending

Firecracker microVMs

Own kernel behind KVM · hardware isolation

Its own kernel per sandbox, for hostile multi-tenant code. Built and tested against a fake VMM; real-KVM e2e and benchmarks are pending, so no numbers yet.

  • Same crabd, same frames, same tools
  • Workspaces become block drives, synced back at teardown
  • Hostile archives are rejected on the way out
  • Jailer confinement for multi-tenant hosts is still to land

03 · Native tools

The tools an agent actually needs

Sixteen tools live inside crabd. File and search tools are native Rust (ignore, globset, grep-searcher), not shell-outs to sed and find. Their schemas are generated from the protocol crate, so they reach your model as-is. Recoverable failures come back as JSON for the model to read; fatal ones stay a Rust error.

Transfer

Timeouts kill the whole tree

Every bash call has a timeout. When it expires, crabd signals the entire process group, so forked children don’t outlive the call. Sandboxes also carry a TTL.

Output is bounded

A runaway log can’t flood the context window. crabd keeps a capped head and tail (32 KiB per stream by default), drops the middle and tells the model it did.

04 · One guest protocol

One wire, every backend

A static, musl-linked daemon called crabd runs inside every sandbox. The host always talks to it the same way: a 4-byte big-endian length, then a JSON-RPC 2.0 message where method is the tool name.

The transport changes with the backend. The bytes don’t. What you test on a laptop is what runs on your servers, and nothing reaches for docker exec.

05 · Meet crabagent

The agent that built this page

It wrote this page from inside a Sandcrab sandbox.

crabagent is a small coding agent whose tools are exactly Sandcrab’s tools. Every bash, file_edit and grep it issues runs inside a Sandcrab sandbox, never on your machine. It exists to exercise the SDK the way a real agent does.

  • Mount a workspace with -w, or a host directory with --mount-host
  • REPL by default, or one-shot with -p
  • Defaults to the ts-dev template (Node, pnpm, bun, TypeScript)
  • Runs against a scripted fake LLM in tests, so the loop is verified without an API key

06 · Quickstart and open source

Your shore, your rules. Apache-2.0.

Sandcrab is a Rust workspace you build and host on your own machines. State lives in a directory you own (~/.sandcrab, or $SANDCRAB_HOME).

  • Apache-2.0Use it, fork it, ship it.
  • Self-hostableYour Docker daemon today, with microVMs on your KVM hosts to follow.
  • Pinned templatesDockerfile + manifest, image integrity checked by SHA-256.
  • Honest limitsKnown gaps and deferred items are listed openly in the repo.

Not yet

  • Egress allowlist. Network is off or unrestricted, nothing in between.
  • Snapshots. Every sandbox starts fresh from its template.
  • MCP. No MCP server yet; tools come through the SDK and CLI.
