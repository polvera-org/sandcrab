01

What Sandcrab is

Sandcrab is a self-hostable Rust sandbox manager and SDK for running untrusted agent code. An agent (or the program driving it) asks for an ephemeral sandbox built from a pinned OCI template, mounts one or more persistent workspaces into it read-write or read-only, runs tools such as bash, file_edit and grep, and throws the sandbox away. The workspace survives, and the host may change its files before the next turn.

Isolation is pluggable through the RuntimeBackend trait. V1 ships two backends: DockerDev (a shared-kernel container, for local dev and CI only, behind an explicit opt-in) and Firecracker (KVM microVMs, hardware isolated). Both talk to the same in-sandbox daemon, crabd, over the same length-prefixed JSON-RPC protocol, so tests on Docker exercise the protocol that production uses. Sandcrab never falls back from one backend to another without being told.

03

Life of a tool call

One wire. The same frames travel over a Unix socket (DockerDev), TCP (tests) and vsock (Firecracker). Follow sandbox.bash("ls") through six hops.

  1. SDK: a typed method, or an LLM's JSON

    Sandbox::bash builds a BashParams and calls the typed path. An agent loop uses tool_dispatch instead, which parses (name, input) into a ToolCall and turns recoverable failures into a JSON {"error":{…}} for the model, keeping Err for fatal ones (sandbox gone, transport lost).

  2. Core: the live sandbox

    sandcrab_core::Sandbox::call_tool refuses calls on a destroyed sandbox, forwards to the per-sandbox CrabdClient, and records the FirstCall timing mark on the first response (success or tool error).

  3. CrabdClient: id, frame, wait

    The client is multiplexed: each request gets a fresh i64 id and a oneshot waiter; a writer task sends frames and a reader task routes responses by id, so concurrent calls on one sandbox may complete out of order. The timeout is the default call timeout (150 s), or a bash timeout_ms plus 10 s of grace when that is longer (client.rs:339 effective_timeout). A timed-out call does not poison the connection.

  4. The frame on the wire

    ADR 0001 §2 fixed the format: a 4-byte big-endian u32 payload length, then that many bytes of JSON-RPC 2.0, with method = tool name and params = the typed params. Zero-length frames and frames over 16 MiB (MAX_FRAME_LEN) are rejected before allocation.

    00 00 00 42u32 BE length {"jsonrpc":"2.0","id":7,"method":"bash","params":{"command":"ls"}}JSON-RPC 2.0 payload (illustrative: 0x42 = 66 bytes)

    Transports: DockerDev returns Endpoint::Unix(socket_dir.join(SOCKET_NAME)), bind-mounted in the container at /run/sandcrab/crabd.sock. Firecracker connects to the VMM's vsock UDS, writes CONNECT 1024\n and expects OK <port>\n (crates/sandcrab-backend-firecracker/src/vsock.rs:23). After that the bytes are identical.

  5. crabd: read, spawn, answer by id

    serve_connection reads frames under a semaphore of max_inflight slots and runs each request on its own task (inside an inner tokio::spawn, so a panicking tool still produces an Internal error response for its id). handle_request answers hello and ping itself and hands every tool to tools::dispatch, a single exhaustive match.

  6. exec::bash: process group, timeout, truncation

    Tide clock: timeout + killpg

    • bash -c runs with .process_group(0) and .kill_on_drop(true); stdin is /dev/null.
    • Timeout = timeout_ms or the default (120 s), capped at the max (1 h).
    • On timeout: SIGTERM the group, wait KILL_GRACE (500 ms), SIGKILL (terminate_group, exec.rs:130). Not an RPC error: timed_out = true, exit_code = None.
    • A GroupGuard SIGKILLs the group if the request future is dropped, and leftovers such as server & are killed after bash exits.

    Few grains: bounded output

    • stdout and stderr are pumped concurrently into a HeadTail buffer (exec.rs:245), at most 32 KiB per stream by default.
    • Memory stays bounded while reading; the middle is replaced by [... N bytes truncated ...], and truncated is set.
    • Output is decoded lossily as UTF-8, so one bad byte cannot break the JSON.

    Precise wording: bash makes its child a process-group leader (setpgid via process_group(0)), not a session leader. setsid is used by process_start in PTY mode (crates/sandcrab-guest/src/tools/process.rs). A descendant that calls setsid/setpgid itself escapes the group kill; the documented backstop is container or microVM teardown.

    The BashResult (exit_code, signal, stdout, stderr, truncated, timed_out, duration_ms) travels back as a JSON-RPC response with the same id; the client's reader task finds the waiter and the typed value surfaces as Result<BashResult> in the SDK.

04

Life of a sandbox

Spawn: everything is checked before the backend is touched

SandboxManager::spawn (crates/sandcrab-core/src/manager.rs:146) runs this sequence:

  1. config.validate(); then the capability gate: require_hardware_isolation on a backend without it → InsecureBackendRejected. Non-empty secrets → PolicyUnenforceable (reserved for Phase 3).
  2. Template resolve from the TemplateRegistry; the network policy defaults to the manifest's. If backend.enforces_network_policy(&network) is false → PolicyUnenforceable (no V1 backend enforces egress_restricted).
  3. Resources = template limits plus overrides; user = config or manifest.
  4. Mount resolution (resolve_mounts, crates/sandcrab-core/src/mounts.rs:98): guest paths normalised, no duplicates or nesting, none under /proc /sys /dev /run/sandcrab /opt/sandcrab. default_cwd = explicit → first rw mount → template workdir.
  5. Leases for each mount (rw exclusive, ro shared); the lease's verified root, (dev, ino) and generation are copied into the ResolvedMount.
  6. backend.spawn(&spec), mark BackendStarted, then a SpawnGuard owns the handle so a cancelled spawn future cannot leak the sandbox.
  7. Ready: wait_ready retries connect + hello (backoff 2 ms ×1.5, capped at 20 ms) until ready_timeout (30 s default). A protocol-version mismatch is fatal. Failure destroys the handle.
  8. The sandbox enters the active map and the TTL reaper task is started if it is not already running.

DockerDev spawn

  • verify_image: the image ID must match the template's sha256 pin (unpinned images refused unless allow_unpinned_images).
  • Per-sandbox socket dir on the host, mounted at /run/sandcrab.
  • Hardened container (§6), entrypoint pinned to /opt/sandcrab/crabd serve --unix /run/sandcrab/crabd.sock; crabd is bind-mounted read-only from the host, never baked into the image.
  • Workspace roots are re-verified with verify_workspace_root before the bind mount is built.

crates/sandcrab-backend-docker/src/backend.rs:339

Firecracker spawn

  • Cached read-only rootfs + a sparse per-sandbox scratch drive (overlayfs in the guest).
  • Each mount becomes an ext4 drive ws<n>: ro images cached, rw images built per spawn.
  • Optional tap from the pre-created pool (only for unrestricted), cgroup v2 leaf, then the VMM API: machine config, boot source, drives, InstanceStart.
  • crabd is PID 1; the host sends InitConfig over vsock control port 1 (init.configure), and init starts crabd serve on port 1024 as the sandbox user.

crates/sandcrab-backend-firecracker/src/backend.rs:203

Destroy: single-flight

Explicit destroy, the SDK drop guard, the TTL reaper and shutdown can all race. SandboxShared::start_teardown takes the live handle out of a Mutex<Option<Live>>, so exactly one caller starts the teardown; it runs on a runtime task (a cancelled caller cannot abort it) and everyone awaits the same outcome on a watch channel. A TeardownGuard publishes an outcome even on panic or runtime shutdown, and removes the sandbox from the active list before waking waiters. If the backend teardown fails, rw leases are released as failed and the workspace is marked dirty.

Backend teardown: DockerDev stops and removes the container and its socket dir with a stop grace. Firecracker first syncs back every rw drive (§5), then stops the VM (graceful init.shutdown, then fallbacks) and cleans the run dir, preserving images whose sync-back failed (crates/sandcrab-backend-firecracker/src/vm.rs:501).

TTL reaper

Tide clock. Default TTL is 30 min (DEFAULT_TTL_SECS). ensure_reaper runs a tokio interval (1 s default) holding only a Weak to the manager, collects expired sandboxes and destroys them through the same single-flight path (manager.rs:349).

Timing marks

Every sandbox carries LifecycleTimings; the phases are the LifecyclePhase enum (crates/sandcrab-core/src/timings.rs:18). The standard phases match the benchmark spec's metric boundaries; backends add custom marks.

05

Workspaces

The model

A Workspace has an id, a name, a generation counter and a backing (crates/sandcrab-core/src/workspace.rs:123):

  • HostDir(PathBuf): an existing user directory, registered canonical; never deleted by Sandcrab.
  • ManagedDir(PathBuf): lives at <state_root>/workspaces/<id>/data (state root ~/.sandcrab, or $SANDCRAB_HOME).
  • BlockVolume(PathBuf): reserved in V1; a backend may attach it directly, host file ops are not implemented.

Mounts are MountMode::ReadWrite or ReadOnly; one sandbox can mount several workspaces at disjoint guest paths.

Window vs. door. ro is a window (look, don't touch: the kernel enforces it on the bind mount or the drive is attached read-only); rw is a door, and only one sandbox may hold it at a time.

Host-side mutation between turns

WorkspaceRegistry::put_file, read_file, delete_file and list_files (exposed through the SDK's WorkspaceClient) let the host add attachments or collect output between agent turns. While a rw lease is held by any process, host mutation fails with WorkspaceBusy unless the caller opts in with HostWriteOptions::force; reads are always allowed. put_file bumps the generation, which invalidates cached read-only images.

Race-free, fd-relative file ops

A rw-mounted workspace is attacker-controlled, and it can change between any two host syscalls (a guest looping renameat2(RENAME_EXCHANGE) to swap a directory with a symlink). So crates/sandcrab-core/src/fsx.rs never checks a path and then re-walks it by name:

  • The root is opened once; every walk is relative to that fd.
  • On Linux the directory walk is a single openat2 with RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS; elsewhere, or when openat2 is unavailable, one openat(O_DIRECTORY | O_NOFOLLOW) per component.
  • Writes go to a fresh O_CREAT | O_EXCL temp file in the target dir fd, then renameat within that fd; deletes use unlinkat on the parent fd.
  • Any symlink on the path, even one pointing inside the workspace, is refused with PathEscape.

Roots: overlap refusal and dev/ino pinning

  • No overlap: workspace roots may not be equal to, an ancestor of, or a descendant of another workspace root or the state root (ensure_no_overlap, crates/sandcrab-core/src/registry.rs:426). Otherwise a sandbox holding the outer one rw could swap the inner one's root. Overlapping entries in older registries are tolerated but cannot be leased.
  • Pinned identity: each directory root is stored with its (dev, ino) (RootIdentity). Every host op and lease reopens it from / with O_NOFOLLOW | O_DIRECTORY per component and compares; a root replaced by a symlink or another directory fails with WorkspaceRootChanged. Backends call verify_workspace_root (registry.rs:400) again right before use.

Leases across processes

WorkspaceRegistry::lease (registry.rs:837) takes non-blocking flocks on <state root>/locks/<id>.mount.lock (exclusive for rw, shared for ro) and <state root>/locks/<id>.rw.lock (held exclusive by the rw lease; host mutation probes it). The lock files live outside the workspace directory, so leasing a registered host directory creates no workspaces/<id>/ entry; remove deletes them. registry.json is written atomically (tmp + fsync + rename) under registry.lock. Releasing a rw lease bumps the generation.

Firecracker: block-volume pack and sync-back

Firecracker has no virtio-fs, so supports_host_dir_mounts = false: the host directory stays the source of truth, copied in at spawn and synced back at teardown (docs/design/firecracker-backend.md §5).

  1. Pack (pack_dir, crates/sandcrab-backend-firecracker/src/workspace.rs:54): a sandcrab-tar-v1-style tar. Symlinks are stored, not followed; special files skipped; setuid/setgid dropped; ownership normalised to the guest user.
  2. Image (build_image, :224): mke2fs -d turns the tar into ext4. Read-only images are cached per (generation, tree fingerprint, owner) by cached_ro_image (:281) and shared by every sandbox mounting that generation.
  3. Export: at teardown the guest's init.export acks with format sandcrab-tar-v1 and streams the rw tree over vsock.
  4. Unpack (receive_export, :393 → sandcrab_core::archive::unpack_safe): hostile input. Absolute paths, .., hard links, devices and FIFOs are rejected; setuid/setgid are refused and modes masked (& 0o777 & !umask); duplicates and missing end-of-archive markers fail the whole archive; byte caps follow the drive size, not a constant; zero runs become holes.
  5. Commit (commit, :433): a ManagedDir is swapped atomically (RENAME_EXCHANGE where available); a HostDir is mirror-applied in place, which is not atomic (documented V1 trade-off). A failed sync-back preserves the guest image and returns an error.
Hermit handoff. Because the workspace outlives the sandbox, a turn in python-dev can write a chart and the next turn in render can mount the same workspace (perhaps ro) and turn it into a PDF.

DockerDev hardening

Built as pure data in build_container_spec, so the whole matrix is unit-tested without a daemon:

Also: runs as the host uid:gid (so bind-mounted files stay editable on the host), published ports bind to 127.0.0.1 only, /tmp is noexec (binaries and shared objects cannot run from it; use $HOME or the workspace), core dumps are disabled so crashes never drop core.* files into a workspace, the entrypoint is pinned to crabd, and disk_mb is not enforced (a warning is logged; overlay2 would need xfs + pquota). Templates & pinning

A template is a standard Dockerfile plus a sandcrab.toml manifest in templates/<name>/. TemplateRegistry::load reads every directory and validates the manifest (crates/sandcrab-core/src/template.rs:18).

TemplateBuilt fromContents
basedebian:trixie-20261104-slim@sha256:…Debian 13 + core utilities

ts-devsandcrab/base:0.1.0 (+ Node 26 and bun stages pinned by digest)Node.js 26, pnpm, bun, TypeScript, vitest, biome, Debian python3; no browser (use render)

What the pin means: the sha256 is the image ID of the local build. It pins integrity (a different image is refused), not bit-for-bit reproducibility, because apt packages are not pinned yet; re-run templates/build.sh --pin after every rebuild. Base images are pinned by digest in the Dockerfiles.

Rootfs pipeline (Firecracker)

  • rootfs::augment appends /sbin/crabd (static musl, sha-pinned) and the needed empty dirs; ownership stays root.
  • rootfs::mkfs runs mke2fs -t ext4 -d <tar> (rootless; strategies native | container | fakeroot).
  • Cached at ~/.sandcrab/cache/rootfs/<key>/{rootfs.ext4, manifest.json} with key = sha256(image_id ‖ crabd_sha256 ‖ PIPELINE_VERSION) (crates/sandcrab-backend-firecracker/src/rootfs/mod.rs:48); the recorded rootfs_sha256 is checked on load.
  • Guest kernel and Firecracker binaries are pinned by SHA-256 in crates/sandcrab-backend-firecracker/src/artifacts.rs and fetched by scripts/fetch-artifacts.sh (or sandcrab doctor --fix).
  • Entry points: scripts/build-rootfs.sh (a thin wrapper), the sandcrab-rootfs binary and sandcrab rootfs.
08

crabagent & the bench harness

crabagent

A minimal, pi-style coding agent (crates/sandcrab-agent/src/lib.rs) whose tools are exactly Sandcrab's tools. It exists to exercise the SDK the way a real agent does.

  • llm::anthropic: Messages API client with SSE streaming, prompt caching and retries; default model claude-sonnet-5-5 (--model / CRABAGENT_MODEL).
  • agent: the tool-use loop, running parallel tool calls through Sandbox::tool_dispatch.
  • session: workspace resolution (-w, --mount, --mount-host), sandbox lifecycle, REPL or one-shot -p (with --keep-alive SECS to hold published ports after the task); template default ts-dev. With a managed workspace at the cwd, npm / pip / Playwright caches go to <cwd>/.cache so installs survive sessions.
  • media: images returned by download (or a binary file_read) reach the model as image blocks, never as base64 text; other binaries are summarised.
  • llm::fake: a scripted LLM, so the loop is tested on the fake backend and real Docker without an API key.

sandcrab-bench

Backend-generic runner for docs/plans/phase-1-mvp.bench-spec.md, documented in docs/bench/README.md.

  • Scenarios: lifecycle, calls, agent-turn, resources, density, drift.
  • Seeded RNG and fixtures, ABAB scheduling, percentile and bootstrap stats, cgroup / /proc sampling, host declaration.
  • Schema-versioned JSON results; the JSON Schema is committed at docs/bench/results/schema.json.
  • V1 measures DockerDev only. Firecracker is wired in but is recorded as unavailable on hosts without /dev/kvm, never substituted.

Where to start

Build, test, lint

Reading order

  1. sandcrab-protocol/src/framing.rs and rpc.rs: the wire, in about 600 lines.
  2. sandcrab-guest/src/tools/exec.rs: the module doc is the bash contract.
  3. sandcrab-core/src/backend.rs then manager.rs: the trait and the lifecycle.
  4. registry.rs (module doc) and fsx.rs: the security-critical host side.
  5. sandcrab-core/src/testing.rs: FakeBackend and the mock crabd (feature test-util), the fastest way to test lifecycle changes.
  6. The e2e suites in crates/sandcrab-sdk/tests/: harness, lifecycle, security, tools, workspace.

Firecracker status

Built, KVM end-to-end pending. The backend, rootfs pipeline, vsock transport, workspace drives, tap pool and CLI wiring are implemented and covered by a fake-VMM suite (crates/sandcrab-backend-firecracker/tests/fake_vmm.rs). The real-KVM tests (firecracker_kvm.rs) exist but are ignored: the planned host (kvm-homelab, a Proxmox VM) exposes no /dev/kvm until nested virtualization is enabled. Flow steps kvm-host and fc-e2e are blocked by maintainer decision.

Rules of the road

  • Every new backend reports honest BackendCapabilities and refuses what it cannot enforce.
  • New tools go in crabd, native Rust (no shelling out to sed/grep/find), with params/results in sandcrab-protocol so the schema reaches LLMs and MCP.
  • Host-side code that touches a workspace goes through fsx; never canonicalize and re-walk.
  • Conventional Commits with crate scope, atomic commits, no .sandcrab/ state committed.
